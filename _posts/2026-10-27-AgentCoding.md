# 前言：为什么需要 Agent Coding 协作规范？

AI Coding 正在从传统的代码补全，发展为能够独立分析需求、修改源码、执行测试、排查问题和维护工程文档的 Agent Coding。

然而，当 AI 参与长期项目开发时，新的工程问题也随之出现：

- **上下文丢失**：新的 AI 会话不了解过去的架构决策、开发进度和遗留问题。
- **协作冲突**：不同 Agent 同时修改相同文件，容易造成代码覆盖、接口冲突或重复开发。
- **工程失控**：AI 为完成局部任务随意调整公共接口、重构其他模块，导致改动范围不可控。
- **知识碎片化**：重要设计和调试经验散落在聊天记录中，难以被团队复用。
- **交付不可验证**：AI 声称任务已完成，但缺少构建、测试和实际验证的证据。
- **人员依赖**：项目依赖某位工程师或某段聊天记录，人员切换后难以快速接手。

因此，长期 AI Coding 的关键并不是如何写出更复杂的 Prompt，而是：

**建立一套由 Git 管理、由文档承载、由测试验证、由人类监督的 AI 协作开发体系。**

本文将从一个空白项目开始，逐步搭建这套体系。

# 第一章：Agent Coding 的核心设计理念

## 1.1 从会话驱动转向项目驱动

传统的 AI 辅助开发通常依赖一个连续的聊天窗口：

用户提出需求 → AI 分析 → AI 修改代码 → 用户继续提问。

这种方式适合短期任务，但不适合作为长期项目的唯一开发机制。

长期开发应采用：

**项目文档 + 实际源码 + Git 历史 + 测试证据 + 当前任务状态 → Agent → 可验证的工程交付。**

其关键区别在于：

| 维度 | 会话驱动开发 | 项目驱动开发 |
|---|---|---|
| 上下文来源 | 聊天历史 | 仓库与任务文档 |
| 规范管理 | 临时 Prompt | 版本化项目规范 |
| 开发进度 | AI 对话记录 | Roadmap 与任务状态 |
| 历史决策 | 人工回忆 | ADR 与 Git |
| 多 AI 协作 | 手工复制对话 | 统一任务和交接机制 |
| 代码隔离 | 同一工作目录 | Git Branch / Worktree |
| 质量保障 | AI 自我判断 | CI、测试和人工 Review |

这里的核心原则是：

**聊天记录是沟通媒介，代码仓库才是项目状态的长期载体。**

## 1.2 五项基本原则

### 原则一：Single Source of Truth（单一可信来源）

同一类信息应有明确的权威来源。

- 产品目标与需求：需求文档。
- 软件设计与架构决策：架构文档和 ADR。
- 实际实现状态：当前源码及 Git 历史。
- 功能完成情况：测试、验收和合并记录。
- 开发计划：ROADMAP。
- 当前工作状态：Task / Handoff。

文档与源码冲突时，Agent 必须识别并报告差异，而不是擅自假设文档描述已经实现。

### 原则二：Context as Code（上下文工程化）

将长期有效的工程知识保存为 Markdown 文件并纳入 Git 版本管理。

上下文应具备：

- 可读性
- 可追溯性
- 可维护性
- 可检索性
- 可跨 Agent 复用

### 原则三：Task Isolation（任务隔离）

每个开发任务必须有明确的目标、边界和验收标准。

对于涉及并行代码修改的任务，应优先采用独立 Git 分支和 Worktree，避免多个 Agent 在同一个工作目录中相互覆盖。

### 原则四：Evidence-Based Development（基于证据的开发）

Agent 完成工作后，不能仅凭代码分析宣称任务完成。

必须区分：

1. 代码已修改。
2. 静态检查已通过。
3. 项目编译已通过。
4. 自动化测试已通过。
5. 真实运行验证已通过。
6. 人工验收已完成。

没有执行的验证必须明确标注为“未验证”。

### 原则五：Human-in-the-Loop（人类最终负责）

Agent 可以进行代码分析、实现、测试和提出设计建议。

但重大架构调整、公共接口变更、生产部署、安全敏感操作以及任务最终验收，应由授权负责人决策。

# 第二章：从零建立标准化 AI 项目

## 2.1 推荐的项目目录结构

下面是一套面向中大型长期项目的推荐结构。

```text
AI-Project/
│
├── README.md
├── AGENTS.md
├── PROJECT_CONTEXT.md
├── ROADMAP.md
├── CHANGELOG.md
│
├── .gitignore
├── .editorconfig
├── .clang-format
│
├── .github/
│   ├── CODEOWNERS
│   └── pull_request_template.md
│
├── docs/
│   ├── architecture/
│   │   ├── SYSTEM_ARCHITECTURE.md
│   │   └── MODULE_INTERFACES.md
│   │
│   ├── decisions/
│   │   └── ADR-0001.md
│   │
│   ├── development/
│   │   ├── CODING_STANDARDS.md
│   │   ├── GIT_WORKFLOW.md
│   │   └── TESTING.md
│   │
│   ├── tasks/
│   │   ├── TASKS.md
│   │   └── TASK-001.md
│   │
│   └── handoffs/
│       └── TASK-001_HANDOFF.md
│
├── src/
├── include/
├── tests/
├── scripts/
└── config/
```

以上是示例结构，不要求所有项目机械照搬。Python、C++、ROS、Web 和多仓库项目可以根据自身特点调整源码目录。

对于规模较小的项目，可暂时只保留：

```text
AI-Project/
├── README.md
├── AGENTS.md
├── PROJECT_CONTEXT.md
├── ROADMAP.md
├── docs/
│   ├── TASK_HANDOFF.md
│   └── TASKS.md
├── src/
└── tests/
```

核心理念是：**先建立最小可运行的协作体系，再随着项目规模增长逐步完善。**

## 2.2 核心文件的职责划分

| 文件 | 核心职责 | 建议维护者 | 更新时机 |
|---|---|---|---|
| README.md | 项目介绍、安装与快速开始 | 模块负责人 | 使用方式变化 |
| AGENTS.md | Agent 的行为和执行规范 | 技术负责人 | 开发规则变化 |
| PROJECT_CONTEXT.md | 项目背景、架构与技术约束 | 架构负责人 | 架构或环境变化 |
| ROADMAP.md | 阶段目标、里程碑和验收要求 | 项目负责人 | 计划调整 |
| TASKS.md | 任务分工、Owner 和状态 | 任务负责人 | 分配及状态变化 |
| TASK_HANDOFF.md | 任务进展、验证证据及下一步 | 当前任务执行者 | 阶段完成或交接 |
| ADR-xxxx.md | 重要架构决策及原因 | 技术负责人 | 关键决策产生 |
| TESTING.md | 测试方法、命令和验收标准 | 测试/模块负责人 | 验证方法变化 |
| CHANGELOG.md | 面向版本的已交付变更 | 发布负责人 | 发布或版本调整 |

**重要区别：**

`AGENTS.md` 属于部分 Coding Agent 支持自动发现的约定；其他 Markdown 文件是团队自定义的项目知识库，需要 Agent 根据任务有选择地读取。

不应要求每个 Agent 在每次修改代码前无条件读取全部文件，否则容易造成上下文浪费和注意力分散。

# 第三章：建立 AGENTS.md —— Agent 的长期行为规范

## 3.1 AGENTS.md 是什么？

`AGENTS.md` 是面向 AI Coding Agent 的仓库指令文件。

它回答的不是“当前要开发什么”，而是：

**AI 在这个项目中应该遵循哪些长期有效的规则？**

典型内容包括：

- 项目目标和工作边界。
- 项目文档入口。
- 源码修改原则。
- 编码及测试规范。
- Git 使用规则。
- 任务完成和交接要求。
- 高风险操作限制。

原则上，AGENTS.md 应保持简洁、稳定和可执行。

不建议把详细架构、完整开发计划和所有历史问题都塞进该文件。

## 3.2 AGENTS.md 推荐模板

下面是可以直接用于新项目的基础模板。

**文件：`AGENTS.md`**

```markdown
# AI Agent Development Instructions

## 1. 项目原则

本项目采用 Agent Coding 辅助开发。

所有 Agent 必须以当前实际源码、
项目文档和明确的用户需求作为工作依据。

禁止根据未经验证的假设宣称功能已实现。

## 2. 上下文读取

开始任务时：

1. 阅读当前目录适用的 AGENTS.md。
2. 根据任务需要查阅：
   - PROJECT_CONTEXT.md
   - ROADMAP.md
   - docs/architecture/
   - docs/tasks/
   - docs/handoffs/
3. 阅读与本任务相关的实际源码。
4. 检查 Git 分支及工作目录状态。

简单任务不需要遍历所有文档。

## 3. 代码修改规范

- 优先遵循现有软件架构。
- 优先复用已有模块与接口。
- 不得无故进行大范围重构。
- 不得修改与任务无关的代码。
- 不得擅自改变公共 API 或通信协议。
- 避免引入不必要的依赖。
- 保持与项目现有代码风格一致。
- 不得覆盖他人尚未提交的修改。

## 4. 任务执行

执行开发任务时：

1. 明确需求、范围和验收标准。
2. 分析现有实现。
3. 制定适度的实施方案。
4. 修改代码。
5. 执行适当的验证。
6. 检查 Git Diff。
7. 汇报修改结果及剩余风险。

只有影响正确实现的关键歧义，
才需要先请求用户确认。

## 5. 测试规范

- 根据实际改动选择必要的测试。
- 不得虚构测试结果。
- 不得将静态检查等同于运行验证。
- 对现有失败和新增失败进行区分。
- 对无法执行的测试说明原因。

## 6. Git 操作

- 修改前检查当前分支和工作区。
- 不得擅自删除或覆盖未提交修改。
- 不得自行执行破坏性的 reset/clean 操作。
- 未经授权，不得 force push。
- 未经授权，不得直接修改受保护分支。
- 不得擅自合并或发布代码。

## 7. 项目文档维护

当任务涉及重要设计决策、跨会话开发、
接口变化或复杂调试时，更新相应文档。

任务交接至少记录：
- 已完成内容
- 修改文件
- 验证结果
- 尚存问题
- 下一步工作

不得将计划中的功能写成已经完成。

## 8. 安全约束

- 不读取或泄露无关的密钥和敏感数据。
- 不将凭据、Token 或私有数据写入仓库。
- 不擅自执行生产部署。
- 不擅自操作真实设备或危险执行机构。
- 高风险操作必须取得明确授权。

## 9. 最终输出

任务完成后，简要说明：

1. 修改内容
2. 关键文件
3. 验证结果
4. 未解决问题
5. 是否更新交接文档
```

## 3.3 AGENTS.md 的维护原则

**应该写入的内容：**

长期稳定的技术约束、代码风格、权限边界、开发流程和必要的文档入口。

**不应该写入的内容：**

某一次 Bug 的排查日志、每周开发进度、过长的模块说明、一次性 Prompt，以及已经失效的历史要求。

当多个子模块存在特殊规范时，可以在相应子目录设置局部 `AGENTS.md`（前提是所用工具支持此机制）。

例如：

```text
src/
├── slam/
│   └── AGENTS.md
├── perception/
│   └── AGENTS.md
└── planning/
    └── AGENTS.md
```

根目录规范适用于全局，局部文件用于说明模块特殊约束；具体优先级应以使用的 Agent 工具规则为准。

# 第四章：建立持久化项目上下文

## 4.1 PROJECT_CONTEXT.md：项目长期记忆

这是整个体系中最重要的自定义文档之一。

它解决的问题是：

**一个全新的 AI Agent，如何快速理解项目是什么、架构如何组织、哪些技术决策不能轻易修改？**

建议记录：

- 项目背景与目标。
- 核心技术栈。
- 当前软件架构。
- 模块职责和依赖。
- 构建及运行环境。
- 重要接口和数据结构。
- 关键技术约束。

- 相关设计文档链接。

### 注意：不要把 PROJECT_CONTEXT.md 变成代码目录的逐文件复述

实际函数签名、实现细节及代码状态，应在任务过程中从源码获取。

对于复杂工程，可以让 Agent 定期检查文档与源码是否一致，但不能把旧文档中的描述直接视作事实。

## 4.2 ROADMAP.md：项目发展路线

ROADMAP 解决的是“未来需要实现什么”，而非“当前 Agent 正在修改什么”。

推荐按照阶段目标和验收要求组织。

```markdown
# ROADMAP.md

## 项目总体目标

描述最终交付目标。

## Phase 1：基础框架

目标：
完成系统基础结构和核心接口。

重点任务：
- 核心模块初始化
- 公共接口定义
- 构建与测试环境搭建

验收标准：
- 项目可构建
- 基础测试通过
- 核心接口完成评审

状态：In Progress

## Phase 2：核心能力

目标：
完成主要功能模块。

重点任务：
- 功能 A
- 功能 B
- 功能 C

验收标准：
- 关键功能测试通过
- 模块集成完成

状态：Planned

## Phase 3：系统集成

目标：
完成系统联调与稳定性优化。

重点任务：
- 模块集成
- 性能测试
- 回归测试

状态：Planned
```

### ROADMAP 与 TASKS 的区别

ROADMAP 记录项目长期目标与阶段成果。

TASKS 记录当前需要分配、执行和验收的具体工作。

例如：

- ROADMAP：完成多传感器融合定位系统。
- TASK：增加相机与 IMU 时间同步处理。
- HANDOFF：当前已修改哪些文件、测试到哪一步、剩下什么问题。

这三个层次不应混为一谈。

ADR（Architecture Decision Record）用于记录重要架构决策。

推荐文件名：

`docs/decisions/ADR-0001-sensor-synchronization.md`

```markdown
# ADR-0001：传感器时间同步方案

状态：Accepted
日期：YYYY-MM-DD
决策人：

## 背景

为什么需要作出该决策？

## 候选方案

方案 A：
优点：
缺点：

方案 B：
优点：
缺点：

## 最终决策

采用哪种方案？

## 决策理由

为什么选择该方案？

## 影响范围

涉及哪些模块和接口？

```

当另一个 Agent 数周后试图修改架构时，可以通过 ADR 理解过去的设计背景，避免反复推翻已确认的方案。

# 第五章：长期开发与跨会话任务交接

## 5.1 为什么不能只依赖 AI 的聊天记忆？

Agent 可能因为以下原因失去原有上下文：

- 上下文窗口达到限制。
- 会话重新开始。
- 更换模型。
- 从 Codex 切换到其他工具。
- 开发任务转交给其他工程师。
- 同一个项目存在多个并行开发会话。

因此，项目应该具备独立于任何 AI 会话的任务恢复能力。

最有效的方案是：

**使用结构化任务记录和交接文档，将正在进行的工作显式持久化。**

## 5.2 TASKS.md：任务管理

```markdown
# 当前任务清单

| ID | 任务 | Owner | 分支 | 状态 |
|---|---|---|---|---|
| TASK-001 | 时间同步优化 | Agent A | feat/TASK-001 | In Progress |
| TASK-002 | 回环检测优化 | Agent B | feat/TASK-002 | Planned |
| TASK-003 | 性能回归测试 | Agent C | test/TASK-003 | Blocked |
```

任务状态建议统一使用：

- `Planned`：已规划。
- `In Progress`：正在执行。
- `Blocked`：存在阻塞。
- `In Review`：等待评审。
- `Verified`：已通过约定验证。
- `Done`：已完成要求的集成与验收。
- `Cancelled`：取消执行。

Owner 可以是工程师，也可以在任务文档中指定执行 Agent，但**最终应有明确的人类负责人**。

对于团队并行开发，推荐每个任务有独立的详细文档。

## 5.3 TASK_HANDOFF：跨 Agent 交接机制

这是避免长期开发中断后“重新分析一遍”的关键。

推荐每个复杂任务维护一份独立交接文件：

`docs/handoffs/TASK-001_HANDOFF.md`

### 推荐模板

```markdown

## 1. 任务信息

- 完成内容 C

- 问题 2
```

### 交接文档的三条强制原则

**第一，事实与计划分开。**

例如：

正确：已调整 IMU 时间戳转换逻辑，编译通过；尚未使用实际数据集验证同步误差。

**第二，交接信息必须与代码关联。**

至少记录分支、关键文件，必要时记录 Commit ID。

否则其他 Agent 无法确认文档对应哪个代码版本。

**第三，只在有意义的节点更新。**

推荐更新时机包括：

- 完成阶段性工作。
- 发现重要问题。
- 产生关键设计决策。
- 任务需要中断或转交。
- 准备提交 PR。
- 完成重要验证。

不需要每修改一行代码都更新文档。

# 第六章：多 AI Agent 与团队协作

## 6.1 多 Agent 协作的三种模式

### 模式 A：串行协作

一个 Agent 完成分析，下一个 Agent 完成实现，第三个 Agent 完成审查。

```text
Architecture Agent
        ↓
Implementation Agent
        ↓
Review Agent
        ↓
Human Approval
```

适用场景：

- 复杂架构调整。
- 大型功能开发。
- 算法设计与代码实现分离。
- 不同模型之间的任务切换。

这是最容易落地的多 Agent 协作模式。

### 模式 B：并行协作

将相互独立的任务分配给不同 Agent。

```text
             Project Lead
                  |
       ┌──────────┼──────────┐
       |          |          |
    Agent A    Agent B    Agent C
       |          |          |
    Module A   Module B   Testing
       |          |          |
       └──────────┼──────────┘
                  |
           Integration Review
                  |
                 Main
```

适用场景：

- 不同模块并行开发。
- 独立 Bug 排查。
- 单元测试与文档编写。
- 多种技术方案评估。

并行任务必须具备清晰的边界，避免多个 Agent 同时修改相同代码。

### 模式 C：主 Agent + 子 Agent

由主 Agent 进行任务规划和结果集成，并向子 Agent 分配独立工作。

常见职责包括：

- 主 Agent：任务拆分与结果整合。
- 子 Agent A：代码探索。
- 子 Agent B：算法或实现方案分析。
- 子 Agent C：测试与风险审查。

这种模式要求使用的工具具备相应的多 Agent 调度能力。

**多 Agent 不是越多越好。**

如果多个任务存在强依赖、频繁修改共享接口或需要持续同步上下文，过度并行反而会增加集成成本。

---

## 6.2 推荐的职责分工

| 角色 | 主要职责 | 可否修改代码 |
|---|---|---|
| Architecture Agent | 架构分析、方案评估 | 默认只读 |
| Implementation Agent | 功能开发、Bug 修复 | 可以 |
| Testing Agent | 测试设计和验证 | 按任务授权 |
| Review Agent | 代码审查、安全与回归分析 | 默认只读 |
| Integration Agent | 分支集成、冲突处理 | 按权限授权 |
| Human Lead | 需求确认、重大决策和最终验收 | 最终负责人 |

这些是逻辑角色，不要求使用六个不同的 AI 模型。

实际使用中，一个 Agent 可以承担多个角色；对于高风险或重大架构修改，建议安排独立审查。

## 6.3 多 Agent 的任务分配规则

每次分配任务至少明确：

1. 任务 ID。
2. 目标与验收标准。
3. 允许修改的目录。
4. 禁止修改的目录。
5. 依赖的接口版本。
6. 对应 Git 分支或 Worktree。
7. 交付物。
8. 测试要求。

例如：

**Agent A：SLAM 前端优化**

- 负责 `src/slam/frontend/`。
- 不修改后端优化接口。
- 输出实现、测试结果和交接记录。

**Agent B：回环检测开发**

- 负责 `src/slam/loop_closure/`。
- 不修改前端状态估计逻辑。
- 需要修改公共数据结构时，先提出接口变更。

**Agent C：测试验证**

- 负责测试用例和评估脚本。
- 不直接改写 A、B 的算法实现。
- 汇总验证证据和回归问题。

这种分工能够减少代码冲突，但不能完全替代集成测试，因为模块之间仍可能存在隐含依赖。

## 6.4 如何处理共享文件和公共接口？

共享接口、构建系统、配置文件和全局数据库结构是最容易产生冲突的区域。

推荐以下机制：

- 每个共享接口明确一个 Owner。
- 接口变更先形成统一定义，再分配实现任务。
- 多个 Agent 不得独立决定同一个接口的不同版本。
- 需要跨模块改动时，由 Integration Owner 协调。
- 公共文档和任务状态的编辑采用明确的 Owner 或顺序合并机制。
- 重要架构变更记录 ADR。

注意：任务登记只是协作约定，并不是技术意义上的分布式锁。

对于真正需要排他保护的资源，应通过分支权限、CI、代码审查或其他工程机制进行约束。

# 第七章：使用 Git Worktree 隔离多个 Agent

## 7.1 为什么推荐 Git Worktree？

如果多个 Agent 在同一个工作目录修改代码，可能遇到：

- 文件被相互覆盖。
- 构建结果互相污染。
- 同一分支出现混杂改动。
- 无法区分修改来源。
- 一个 Agent 的操作破坏另一个 Agent 的未提交工作。

Git Worktree 可以让同一个 Git 仓库同时关联多个独立工作目录，每个目录检出自己的分支。

相比在同一目录频繁切换分支，Worktree 更适合并行开发。

## 7.2 Worktree 实践示例

假设主项目为：

```text
~/projects/robot/
```

先在主工作区更新主分支：

```bash
cd ~/projects/robot

git status
git fetch origin
git switch main
git pull --ff-only origin main
```

执行前确认主工作区中没有会阻碍切换或拉取的未提交修改。

创建任务 A 工作目录：

```bash
git worktree add \
  -b feat/TASK-001-sync \
  ../robot-task-001 \
  main
```

创建任务 B 工作目录：

```bash
git worktree add \
  -b feat/TASK-002-loop \
  ../robot-task-002 \
  main
```

此时：

```text
projects/
├── robot/
│   └── main
│
├── robot-task-001/
│   └── feat/TASK-001-sync
│
└── robot-task-002/
    └── feat/TASK-002-loop
```

Agent A 在 `robot-task-001` 工作。

Agent B 在 `robot-task-002` 工作。

两者可以并行修改，不会直接覆盖彼此的工作目录。

但如果两个任务修改了同一个逻辑接口，最终集成时仍然需要解决兼容性和合并冲突。

## 7.3 提交与集成

各 Agent 在自己的工作目录完成修改后：

```bash
git status
git diff --check
git diff
```

完成验证后，由具备相应权限的执行者提交：

```bash
git add <task-related-files>

git commit -m "feat(slam): improve sensor sync"
```

推送任务分支：

```bash
git push -u origin feat/TASK-001-sync
```

随后创建 PR 或 MR，由团队执行代码审查和自动化验证。

集成流程推荐为：

```text
Feature Branch
      ↓
   Pull Request
      ↓
  Automated CI
      ↓
  Code Review
      ↓
   Integration
      ↓
     Main
```

合并后，在确认对应工作区已经没有需要保留的未提交修改时，清理 Worktree：

```bash
git worktree remove ../robot-task-001
```

必要时再清理已合并的本地分支。

## 7.4 Worktree 注意事项

- 不要将同一个本地分支同时强行检出到多个 Worktree。
- 不要未经检查就删除存在未提交修改的 Worktree。
- 不同 Worktree 可能仍然共享外部数据、运行端口或硬件资源。
- 对于 C++、ROS 等项目，尽量让每个 Worktree 使用独立构建目录。
- 不建议多个 Agent 同时操作同一台真实机器人或共享硬件设备。
- 切勿假设 Git 隔离能够自动隔离数据库、Docker 容器和外部服务。

# 第八章：标准化 Agent Coding 开发流程

推荐采用以下工作流。

## Step 1：任务定义

由项目负责人或任务负责人明确：

- 具体需求。
- 功能边界。
- 相关模块。
- 验收标准。
- 优先级。
- 风险等级。

对于复杂任务，建立独立 TASK 文档。

## Step 2：上下文加载

Agent 读取适用的 `AGENTS.md`。

随后按任务需要加载项目上下文、任务文档、相关设计决策及实际源码。

不要把无关的历史内容全部塞入上下文。

## Step 3：现状分析

在编写代码之前确认：

- 当前已有实现。
- 调用关系。
- 可复用的功能。
- 潜在副作用。
- 影响范围。
- 验证方式。

对于复杂变更，先给出实施方案。

对于小规模且没有关键歧义的任务，可以直接执行。

## Step 4：实现

根据分析修改相关代码。

要求：

- 优先最小必要修改。
- 避免无关重构。
- 不覆盖其他 Agent 的修改。
- 保持接口一致。
- 发现超出任务范围的问题时单独记录。

## Step 5：验证

根据任务类型进行适当验证。

| 验证层次 | 验证内容 |
|---|---|
| L1 | Diff 检查、格式检查 |
| L2 | 静态分析、类型检查 |
| L3 | 编译与构建 |
| L4 | 单元测试 |
| L5 | 集成测试 |
| L6 | 实际数据或硬件验证 |
| L7 | 人工验收 |

并非每个任务都必须执行全部层次。

例如：

- 文档修改：通常只需格式与内容检查。
- 小型 Bug 修复：应优先执行相关回归测试。
- 公共接口修改：需要构建及依赖模块验证。
- SLAM 算法修改：通常需要数据集回归和精度评估。
- 机器人运动控制修改：除仿真验证外，还应按照安全规程进行实机测试。

## Step 6：独立 Review

建议重要任务至少经过一次独立审查。

Review 重点包括：

- 是否满足原始需求？
- 是否破坏现有功能？
- 是否引入不必要复杂度？
- 是否修改了不相关模块？
- 是否存在竞态、资源泄漏或错误处理遗漏？
- 测试是否充分？
- 文档是否与代码一致？

AI Review 是辅助机制，不能替代必须由人类完成的审批。

## Step 7：更新任务状态及交接记录

对于长期任务：

- 记录实际完成的工作。
- 记录测试证据。
- 记录关键技术决策。
- 记录尚未解决的问题。
- 更新下一步任务。

交接完成后，其他 Agent 应能够在新的会话中恢复工作。

## Step 8：合并与验收

只有满足项目约定的检查和审查条件后，才能合并到受保护分支。

“代码已提交”不等同于“功能已验收”。

# 第十章：质量保障、安全与工程治理

## 10.1 建立 Definition of Done

Definition of Done（DoD）是团队统一的任务完成标准。

建议包括：

- [ ] 需求与任务目标一致。
- [ ] 修改范围符合约定。
- [ ] 不包含意外修改。
- [ ] 必要的检查和测试已经执行。
- [ ] 验证结果真实记录。
- [ ] 重要接口变更已评审。
- [ ] 必要文档已同步。
- [ ] PR/MR 审查通过。
- [ ] 达到约定的集成或验收要求。

不同任务可以使用不同的 DoD。

不应将“AI 已输出最终答复”当作完成标准。

## 10.2 建立 CI 质量门禁

根据项目需要逐步引入：

- 自动格式检查。
- 静态检查。
- 编译检查。
- 单元测试。
- 集成测试。
- 依赖和安全扫描。
- 回归测试。
- 性能基准测试。

对于机器人项目，可进一步增加：

- SLAM 轨迹精度（ATE / RPE）评估。
- 定位丢失率与重定位成功率。
- 回环前后地图一致性。
- CPU / GPU / 内存占用。
- 算法实时性和延迟。
- 不同 ROS bag 数据集回归。
- 规划与控制安全边界检查。

关键指标必须与固定测试环境、数据集版本和评估脚本关联，以避免不同 Agent 得出不可比较的结论。

## 10.3 按风险等级控制 Agent 权限

| 任务等级 | 示例 | 推荐控制 |
|---|---|---|
| 低风险 | 文档、注释、局部格式调整 | 自动检查 |
| 中风险 | 局部算法优化、普通 Bug 修复 | 自动测试与 Review |
| 高风险 | 公共接口、跨模块重构 | 技术负责人审批 |
| 关键风险 | 生产部署、机器人安全控制、敏感配置 | 明确授权与专门验收 |

尤其对于真实机器人，AI 的代码分析、仿真验证和实际设备操作应使用不同权限边界。

## 10.4 数据与权限安全

团队使用 AI Coding 时，应明确：

- 仓库访问权限按最小授权原则配置。
- 生产密钥与密码不能直接写入 Prompt 或代码。
- 敏感数据应使用获准的存储和访问方式。
- 第三方代码、数据集和模型需要遵守许可协议。
- Agent 的终端操作与外部网络访问应受到合理约束。
- 危险 Git 操作、发布与真实设备控制应设置人工审批。

对于企业内部项目，应同时符合公司的代码保密与数据安全制度。

# 第十一章：完整案例——机器人 SLAM 项目的多 Agent 协作

以一个 LiDAR–Vision–IMU 融合 SLAM 项目为例。

项目需要同时推进三个任务：

**TASK-101：优化 LiDAR–IMU 时间同步**

目标：

提高雷达与 IMU 的时间关联一致性，避免点云运动补偿受到错误时间匹配的影响。

主要开发范围：

- 传感器时间管理。
- IMU 数据缓存。
- 数据同步逻辑。

**TASK-102：增加视觉回环检测**

目标：

在现有回环检测系统中增加视觉约束能力。

主要开发范围：

- 图像关键帧描述。
- 候选回环检索。
- 回环约束生成。

**TASK-103：建立 SLAM 评估体系**

目标：

统一不同数据集上的 SLAM 评估方法。

主要开发范围：

- ATE / RPE 评估。
- 数据集配置。
- 评估结果导出。

## 11.1 任务准备

项目负责人先确认：

- 当前公共接口。
- 工作分支基线。
- 三个任务之间的依赖关系。
- 各任务验收标准。
- 允许修改的文件范围。

然后创建三个任务记录。

## 11.2 多 Agent 分工

Agent A：

负责时间同步模块，在独立 Worktree 中开发。

Agent B：

负责视觉回环检测，在另一 Worktree 中开发。

Agent C：

负责评估脚本与自动化测试。

技术负责人：

负责公共接口审核和最终集成。

如果 Agent A 需要修改 IMU 公共消息结构，必须先协调受影响模块。

## 11.3 阶段性交付

Agent A 完成修改后，交付：

- 时间同步代码。
- 构建结果。
- 数据集测试结果。
- TASK-101 Handoff。
- 独立任务分支。

Agent B、C 采用相同模式。

## 11.4 集成与回归

Integration Agent 在获准的集成环境中检查：

1. 三个任务是否使用兼容接口。
2. 是否存在冲突修改。
3. 项目能否完整构建。
4. 单元及集成测试是否通过。
5. SLAM 数据集回归指标是否异常。
6. 文档与最终实现是否一致。

涉及融合前端、回环和全局优化的修改，还应特别关注修改前后的精度、实时性和退化场景表现。

## 11.5 人工验收

由技术负责人审核实际指标及剩余风险。

只有满足约定验收标准后，才将任务标记为 Done。

此时，即使 Agent A、B、C 的会话全部结束，后续开发者仍可以从项目仓库恢复完整的开发状态。

# 第十二章：团队落地路线

对于已经有 Git 仓库和成熟源码的团队，不建议一次性建立大量流程。

推荐分四个阶段推进。

## 阶段一：建立最小协作规范

目标：

让 Agent 在不同会话中能够稳定理解项目。

完成：

- AGENTS.md
- PROJECT_CONTEXT.md
- ROADMAP.md
- 基础构建与测试说明

验收：

新 Agent 能独立定位核心模块、找到构建方法，并理解基本开发约束。

## 阶段二：建立跨会话交接机制

目标：

复杂任务中断后能够直接恢复。

完成：

- TASKS.md
- TASK_HANDOFF 模板
- 任务状态规范
- Prompt 模板

验收：

不同 Agent 能根据任务记录与实际代码接手工作，且不会重复已经完成的开发。

## 阶段三：实现多人、多 Agent 并行开发

目标：

降低任务冲突和集成成本。

完成：

- Git 分支策略
- Git Worktree
- 模块与文件 Owner
- PR/MR 审查流程
- 公共接口变更规范

验收：

至少两个独立任务能够并行开发，并通过可审查的方式完成集成。

## 阶段四：完善自动化质量体系

目标：

将“AI 认为完成”升级为“工程证据证明完成”。

完成：

- CI 自动化检查。
- 测试与验收标准。
- 架构决策记录。
- 自动化回归验证。
- 必要的代码安全检查。

验收：

主要功能变更均有相应的验证证据，重要质量门禁不依赖 Agent 自我报告。

# 第十三章：常见错误与最佳实践

| 常见错误 | 推荐实践 |
|---|---|
| 把所有知识塞进 AGENTS.md | 保持 AGENTS 简洁，其他信息按需读取 |
| 长期依赖同一个聊天窗口 | 将状态外部化到 Git 和文档 |
| 每次重新分析整个项目 | 先读取相关交接记录，再核查代码 |
| 多个 Agent 共用工作目录 | 独立 Branch / Worktree |
| 多个 Agent 同时修改公共接口 | 明确接口 Owner，先评审再实现 |
| AI 自行扩大修改范围 | 使用任务边界和允许修改范围 |
| AI 宣称已完成就直接合并 | 使用测试证据和 PR Review |
| 每次对话更新全部文档 | 只更新有意义的变化 |
| 文档与源码冲突时相信旧文档 | 以源码及实际验证核查事实 |
| 引入大量重复的规范文件 | 维护最小必要的可信知识库 |
| 无限制增加并行 Agent 数量 | 根据模块独立性决定并发规模 |
| 强制每个任务完成所有测试 | 按风险选择适当验证层次 |

# 第十五章：总结

Agent Coding 的长期价值，不仅在于提升单次编码速度，更在于改变团队组织软件开发的方式。

传统软件工程强调代码规范、版本管理、测试和团队协作。

Agent Coding 并没有使这些原则失效，反而对它们提出了更高要求。

一个成熟的 Agent Coding 项目，应具备以下能力：

**1. 可理解（Understandable）**

新加入的工程师或 Agent 能够快速理解项目。

**2. 可持续（Sustainable）**

开发不会因为某次会话结束或模型切换而中断。

**3. 可协作（Collaborative）**

不同工程师和 Agent 能够在明确边界内并行开展工作。

**4. 可追溯（Traceable）**

重要代码、设计决策、测试结果及任务进展都有据可查。

**5. 可验证（Verifiable）**

功能是否完成，由工程证据决定，而不是由 Agent 的文字总结决定。

**6. 可治理（Governable）**

复杂架构、关键接口、敏感操作和最终交付始终处于明确的责任与授权体系之下。

## 最终推荐

对于长期 AI 项目，建议首先建立以下五项核心基础：

| 核心基础 | 解决的问题 |
|---|---|
| AGENTS.md | Agent 应如何开发 |
| PROJECT_CONTEXT.md | Agent 如何理解项目 |
| ROADMAP.md | 项目接下来要做什么 |
| TASK + HANDOFF | 如何恢复和交接长期任务 |
| Git Branch + Worktree + Review | 如何实现隔离开发和安全集成 |

这五项构成最小可行的协作底座。

在此基础上，逐步增加 ADR、自动化测试、CI、权限治理和多 Agent 编排，而不是一开始就构建过度复杂的流程。

**核心理念：让 AI 负责执行，让工程规范保持一致，让 Git 保存事实，让测试证明结果，让人类掌握决策。**
