# 引言

最近接触 OpenClaw、LangGraph、Skill、MCP 这类词的频率明显上升。名词一多，就很容易陷入「每个词都很眼熟，串起来却说不清」的状态：Agent 到底是模型还是程序？Function Calling 和 MCP 是不是一回事？Skill 又该放在哪一层？

本博文尝试把这些概念重新组织成一条可读的主线，重点不在追新词，而在弄清：

1. 每个名词解决的是哪一类问题；
2. 它们分别落在人、程序、模型、工具之间的哪一段接口上；
3. 哪些概念容易被拿来对比，其实并不在同一维度。

# 一条主线：先有接龙，再有系统

如果把智能体相关技术压成一句不太严谨、但很管用的话：

~~~
大模型负责「在不确定处做判断」；
程序负责「把确定的事做完」；
中间那一层 Agent，大多是在帮人少直接跟模型硬磨。
~~~

更具体一点，可以按下面这条生长线来看：

1. 先有 **LLM**：只会按上下文续写下一个 token；
2. 再有 **Prompt / Context / Memory**：把单次接龙包装成可用的对话；
3. 然后出现 **Agent**：用程序代理多轮交互，并接上外部能力；
4. 接着分化出两套「约定」：
   * **Function Calling**：Agent 和模型之间怎么说话；
   * **MCP**：Agent 和工具服务之间怎么对接；
5. 再往后，是多步任务如何固化：**LangChain / Workflow / Skill / 纯 Agent**；
6. 最后落到产品形态：CLI、IDE 插件、桌面助手等。

# 对话层：Prompt、Context、Memory

## LLM 本身能做什么

LLM 的基本能力是条件生成：给定前文，预测后续。把它单独拿出来用，最朴素的形态就是「文字接龙」。之所以后来看起来像能聊天，是因为工程上人为切出了角色边界——把输入输出组织成问答轮次。

这里有个很关键、却常被忽略的约束：

* 模型调用本身通常仍是「一次请求、一次回复」；
* 所谓多轮对话，往往并不是模型内部真的记住了你，而是系统在下一次请求前，把历史内容重新塞进上下文。

## Prompt / Context / Memory 分别指什么

| 概念 | 更贴切的理解 |
|---|---|
| **Prompt** | 这一次真正送进模型的输入内容 |
| **Context** | Prompt 中偏背景、约束、资料的那一部分 |
| **Memory** | 为了维持连续性，而把历史对话（或其摘要）重新写入 Context 的机制 |

因此，Memory 不是模型自带的神秘长期记忆，而更像一种「上下文管理策略」：完整回放、摘要压缩、关键事实抽取，都是在有限窗口里做取舍。

> **NOTE：**  
> 后面几乎所有花活——搜索、RAG、Skill 说明文档——都可以看成同一种动作的变体：**自动往 Prompt 里补 Context**。


# 代理层：Agent 到底是什么

Agent 这个词容易被讲得很科幻。回到工程现实，它更接近：

* 夹在「用户」和「模型」之间的一层程序；
* 负责组织提示词、维护状态、调用工具、汇总结果；
* 把那些不必反复问模型的确定步骤，用代码固定下来。

所以我更愿意把它理解成「编排器 + 传话筒」，而不是「另一个更聪明的大脑」。模型负责语义判断；Agent 负责把判断落到可执行动作上。

早期一些所谓 Agent，实现上可能只是多包了一层 Prompt 模板。名词很新，底层未必复杂——这也是后来大家对概念通胀格外警惕的原因之一。


# 能力扩展：Search 与 RAG

模型权重里没有的信息，就需要从外部拿。视频里把这类能力统称为广义的 **Search**，其中常见两类：

1. **Web Search**：联网查公开信息；
2. **RAG（Retrieval-Augmented Generation）**：先从本地文档/知识库检索相关片段，再把片段塞进上下文，让模型基于检索结果回答。

RAG 通常依赖 **向量数据库**：不是按精确字段匹配，而是按语义相似度召回。它解决的是「模型没见过 / 记不住私有资料」的问题，并不能自动保证事实正确，检索质量仍然决定上限。

# 两套容易混的约定：Function Calling 与 MCP

这是最常见的混淆点之一。两者都叫「约定」，但约定的对象不同。

## Function Calling

面向 **Agent ↔ LLM**：

* 目标：让模型按程序可解析的格式表达「我想调用什么」；
* 常见表现：输出结构化 JSON，而不是自由发挥的自然语言；
* 类比：前后端约定好请求体字段，后端才能稳定解析。

没有这类约定，Agent 就得靠脆弱的自然语言解析去猜模型意图，工程上很难做稳。

## MCP（Model Context Protocol）

面向 **Agent ↔ 工具服务**：

* 目标：规定工具如何被发现、如何被调用、如何返回结果；
* 常见动作：列出工具列表、执行某个工具、拿回结果；
* 类比：服务间的接口文档 / RPC 协议。

当工具还写死在 Agent 进程内部时，未必需要独立协议；一旦工具拆成可复用服务，就需要一套发现与调用规范，MCP 讨论的大致就是这类问题。

## 为什么不能互相取代

| | Function Calling | MCP |
|---|---|---|
| 连接两端 | Agent 与模型 | Agent 与工具服务 |
| 解决什么 | 模型输出如何被程序读懂 | 工具如何被发现和调用 |
| 是否同层 | 否 | 否 |

所以「MCP 会不会取代 Function Calling」这个问题，本身就有点错位：一个管模型怎么说话，一个管工具怎么接线。


# 流程如何固化：从硬编码到纯 Agent

现实任务很少是单轮问答。比如：从英文 PDF 抽文本 → 翻译成中文 → 存成 Markdown。这类多阶段流程，至少有四种常见落法。

## 1. LangChain 一类编程编排

用代码把步骤写死。优点是稳定、可测、可复现；缺点是对输入输出组合爆炸不友好——PDF/Word/TXT 进、Markdown/HTML/图片出，若每一种组合都手写链路，维护成本会很快上升。

## 2. Workflow / 工作流

把编程换成低代码拖拽。对非程序员更友好，改流程也直观一些，但本质仍偏「程序控制走向」：分支一多，画布一样会复杂。

## 3. Skill

折中方案大致是：

* 准备一个目录，放好常用脚本；
* 用 `SKILL.md`（或同类说明文件）把流程、约束、可选脚本写清楚；
* Agent 读取说明后，按任务自行选择脚本并执行。

它常被概括成「Prompt 加载器 + 可运行脚本」。相对纯硬编码，多了灵活空间；相对完全放养的 Agent，又多了文档与脚本边界，不至于每一步都重新发明轮子。

> **NOTE：**  
> Skill 和 MCP 也不是同一维度。Skill 更像「如何组织任务说明书与本地能力」；MCP 更像「如何对接外部工具服务」。可以把工具用法写进 Skill 文档，从而在部分场景弱化对独立 MCP 服务的依赖，但这不等于两者可以简单划等号。Skill 更适合拿去和 LangChain / Workflow / 纯 Agent 比较。

## 4. 纯 Agent 自由发挥

把目标直接丢给 Agent，让它自己拆步骤、自己找工具、必要时自己写脚本。柔性最高，也最不稳定：Token 消耗大，过程不可控，简单任务被复杂化的风险也更高。

可用一句话记住这条谱系：

~~~
越靠左，越稳、越死；
越靠右，越活、越飘。
选型的关键不是谁更新，而是任务有多稳定、能允许多少不确定性。
~~~


# SubAgent：不是更多智能，而是上下文隔离

复杂任务里，主对话窗口很容易被中间过程撑爆。SubAgent 的常见动机很务实：

* 把相对独立的子任务丢给子代理执行；
* 子过程产生的细节上下文，不全部回流主对话；
* 主 Agent 只回收必要结论。

因此，SubAgent 首先是 **上下文隔离与任务拆分**，不必先把它理解成「更高级的多智能体社会」。

再补一张简表：

| 对比 | 结论 |
|---|---|
| Function Calling vs MCP | 不同接口层，不能互相替代 |
| Skill vs MCP | 不同问题域；Skill 管任务说明书/脚本组织，MCP 管工具服务协议 |
| Skill vs Workflow / LangChain | 同属「多步任务如何固化」，可比 |
| Agent vs LLM | Agent 是编排与执行层，LLM 是推理与生成引擎 |
| Memory vs 模型记忆 | 多数产品里的 Memory，本质是 Context 管理 |


# 产品形态为什么突然重要

同一套 Agent 能力，可以长成完全不同的产品体验：

* 命令行 CLI；
* 编程 IDE 内的编码助手；
* 接入社交软件、带定时任务与 Skill 管理页的桌面助手。

最近 CloudBot / OpenClaw 一类产品引起关注，并不一定因为底层出现了全新智能原理，而往往因为：

* 降低了配置门槛；
* 把 Agent 从「电脑里的后台服务」变成「能被普通人感知和操作的助手」；
* 在社交通道、定时任务、Skill 管理等处补齐了使用闭环。

这也回到一个更朴素的判断：**便利性常常比概念纯度更决定扩散速度**。对普通用户而言，让他去手动安放 Skill 目录、配置 MCP、填写各类 API Key，本身就是很高的摩擦。


# 小结

如果只保留几句自己用的判断：

1. **LLM** 是生成引擎；**Agent** 是编排与代理层。  
2. **Prompt / Context / Memory / RAG / Skill 文档**，很多时候都在做同一件事：给模型补上下文。  
3. **Function Calling** 约定模型怎么说话；**MCP** 约定工具怎么接线。  
4. **LangChain → Workflow → Skill → 纯 Agent**，是稳定性与灵活性的连续谱，不是新旧取代关系。  
5. 选型先问任务稳不稳、错了代价大不大，再问该不该上更新的名词。

后续如果继续写实践向笔记，会更适合落到具体系统（例如 OpenClaw 的 Skill 组织、MCP 接入，或 LangGraph 的状态图编排）上，把这篇的概念地图逐项对上代码与配置。
