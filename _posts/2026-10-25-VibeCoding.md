> **NOTE：**
> 建议采用AI(Cursor or Codex)+Git来共同管理代码
> 1. 重要任务先规划，再允许修改代码
> 2. Git 是长期维护的安全底座

# 引言

很多人习惯这样使用 VibeCoding (以一个SLAM工程为例子)：

上午让它修改 IMU 预积分，中午修改视觉残差，下午优化 Local Mapping，晚上接着修改时间同步。

第二天继续打开同一个对话，发现它越来越容易出现重复分析、遗漏约束、修改无关模块等情况。

这不一定是模型本身能力下降，也可能是长期对话累积了大量旧日志、失败尝试及过期信息，导致上下文管理变得困难。

因此，我的建议是： **一个独立开发任务对应一个 Codex 对话，跨对话依靠项目文件交接。**


# 首次初始化项目

让 AI 认识你的项目，并建立长期维护机制。我建议将对话命名为`00 - 项目初始化与长期开发规范`。

这个对话需要完成三个任务：
1. 分析项目现有代码和文档，建立 AGENTS.md。
2. 基于实际代码建立 PROJECT_CONTEXT.md。
3. 建立每次任务结束时的交接机制。


* 提示词 A：项目首次初始化 (适用于第一次打开已有代码仓库，或接手新的长期研发项目。)

```bash
你将作为当前代码仓库的长期研发助手。

请首先分析仓库结构、Git 状态、核心模块、
构建与测试方式，并建立长期维护机制。

创建或完善：
1. AGENTS.md：长期开发规范
2. PROJECT_CONTEXT.md：项目真实架构和状态
3. docs/TASK_HANDOFF.md：任务交接记录

要求：
- 基于实际源码，不能猜测实现状态。
- 优先复用现有文档，避免重复。
- 将项目事实与未来研发计划分开。
- 在 AGENTS.md 中明确任务开始、结束和交接规则。
- 不修改算法代码，不自动提交或推送 Git。

请完成初始化并汇报。
```

初始化后，建议你的仓库先保持这种简单结构：

```bash
Work_Space/
├── AGENTS.md
├── PROJECT_CONTEXT.md
├── README.md
├── docs/
│   └── TASK_HANDOFF.md
├── src/
├── include/
├── config/
└── ...
```


| 文件 | 主要用途 | 重要的区分|
|----------------------|---------------------- |-------------------------------|
| `AGENTS.md`          | Codex 的长期开发规范   | Codex 开发时必须遵守的规则 |
| `PROJECT_CONTEXT.md` | 项目背景与技术架构     | 已经实现的功能 |
| `ROADMAP.md`         | 未来计划与开发任务     | 未来准备实现的功能 |
| `TASK_HANDOFF.md`    | 最近一次任务的开发交接 | 某次任务开发到一半、遇到什么问题 |


# 开始新任务

新建一个窗口，并重命名对话的名字，方便记录：

* 提示词 B：新任务开始（商量方案）

```bash
开始新任务： ***

请遵循 AGENTS.md，按需读取
PROJECT_CONTEXT.md 和 docs/TASK_HANDOFF.md，
并核实当前 Git 与源码状态。

本轮先只读分析：
1. ***
2. 现有问题、边界情况和潜在风险。
3. 最小修改方案。

先提供技术分析和开发计划，
未经确认不要修改代码。
```

对于这种可能涉及多个文件的复杂任务，可以在输入框使用 /plan 切换到 Plan Mode，让AI先提出计划，再进入实现。

2. 确定方案后，在同一个对话中继续

* 提示词C：任务执行（开始写代码）

```bash
我同意上述开发方案，请开始实施。

要求：
1. 按计划分阶段修改代码。
2. 尽量维持现有接口和系统行为。
3. 每完成一个阶段进行对应验证。
4. 若发现需要改变核心算法或技术路线，
   先说明原因，不要擅自改变。
5. 完成后汇报修改文件、测试结果与遗留风险。

本轮先不提交 Git。
```

接下来可以在这个对话内持续交流，包括询问某个函数的作用、纠正 Codex 的实现、分析编译报错，以及要求它进一步优化。
只要仍在解决同一个任务，就可以继续使用当前对话。

3. 问题解决后，结束当前的对话

当问题已经解决，源码已经修改，编译通过，准备开展下一个模块时，此时不要直接关闭对话。


* 提示词 D：任务结束与交接

```bash
本轮任务准备结束，请执行开发交接。

1. 对照目标检查完成情况。
2. 总结修改文件和关键技术决策。
3. 汇报编译、测试及实验验证结果。
4. 更新 docs/TASK_HANDOFF.md。
5. 如有重大项目变化，更新 PROJECT_CONTEXT.md。
6. 非必要不修改 AGENTS.md。
7. 检查文档与实际代码是否一致。
8. 给出下一轮对话的交接摘要。

禁止自动提交或推送 Git。
```

这里的关键不是让 AI 写一大篇总结，而是让它保存下一轮开发仍然需要知道的信息。

4. 下一轮任务的开启

* 提示词 E：下一个任务启动 

```bash
开始新的独立开发任务。

请遵循 AGENTS.md，按需读取项目背景和最近的
TASK_HANDOFF.md，并检查当前 Git 和实际代码。

上一轮任务已结束，只继承相关技术约束。

本轮任务：Local Mapping 视觉重投影因子优化。

请先定位实现、分析算法及优化空间，
提出开发计划和验证方法。

第一阶段只分析，不修改代码。
```

这样一来，新的AI对话不需要重新看几百轮旧消息，也能理解必要的项目背景。


# 什么时候开新对话，什么时候继续旧对话？

| 情况 | 建议 |
|------|------|
| 继续调试当前时间同步 Bug | 留在原对话 |
| 当前方案修改后出现编译错误 | 留在原对话 |
| 当前任务尚未通过测试 | 留在原对话 |
| 时间同步完成，开始开发回环检测 | 新建对话 |
| 新增一个与当前任务无关的功能 | 新建对话 |
| 长对话仍在解决同一复杂任务 | 可以压缩上下文后继续 |
| 需要同时修改两个独立模块 | 分别建立对话，最好隔离工作目录 |

# 其他对话的话术：
    
```bash
• 你对于我的这个需求还有没有什么不明白的，有的话你就提出来。如果没有的话，你先给我列一下实现这个需求的任务列表
• 你对于我的这个需求还有没有什么不明白的，有的话你就提出来。如果没有的话，你开始执行吧（请注意，修改了代码后，不需要编译和运行，只需要确保实现没错即可，我来编译验证）
• 你对于我的这个需求还有没有什么不明白的，有的话你就提出来。如果没有的话，你开始执行吧（请注意，先分析，先不改代码）
```
